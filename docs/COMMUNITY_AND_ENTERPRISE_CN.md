# TARCS-Mem 社区版与企业服务方向

[English](COMMUNITY_AND_ENTERPRISE.md)

TARCS-Mem 的开源仓库就是 Community Edition（社区版）。社区版应当让用户在没有商业
合作的情况下，也能完成一次有价值的本地治理流程。未来收入来自企业级运行、私有系统接入、
持续支持和可验证的落地结果，而不是故意拿走社区版的核心治理能力。

本文描述的是产品方向。标为“规划”的能力尚未在仓库中实现，也不构成交付承诺；是否开发，
应由 Design Partner 的真实需求验证。

## 免费版保留什么，增值服务保留什么

| 能力 | Community Edition（MIT，当前可用） | Enterprise / 增值服务（规划或按项目交付） |
| --- | --- | --- |
| 治理内核 | GuardWrite、GuardRead、TARCS 排序、时间/版本/冲突治理、拒答和引用校验 | 企业策略建模、威胁模型评审和迁移支持 |
| 安全基线 | 租户字段、角色 ACL、数据分级、凭证阻断、PII 脱敏和云端出境拦截 | OIDC/SSO、SCIM、可信身份、企业 RBAC 和策略管理 |
| 存储与部署 | SQLite、Docker、本地 API 和 v0.8 治理控制台 | PostgreSQL/高可用、多租户控制面、备份恢复和托管升级 |
| 集成 | MCP v2、OpenAI 兼容网关、LangChain/LlamaIndex、Qdrant、Confluence Cloud | SharePoint、ServiceNow、Salesforce、企业私有 Confluence 流程和连接器 SLA |
| 可观测与审计 | 隐私安全 Trace、Prometheus 指标和本地审计历史 | SIEM/OTLP、留存/法律保全、合规证据包和运营看板 |
| 评测 | 合成治理用例和仓库内的 FiQA 有限候选池报告 | 企业专属质量、风险、成本评测和周期性报告 |
| 支持 | GitHub Issue、公开文档和社区讨论 | 付费试点、架构评审、私有部署、培训、支持与 SLA |

判断一项能力是否适合收费，不看它“高级不高级”，而看它是否需要客户私有环境、持续运维、
组织专属集成或明确的合规/支持责任。权限、冲突、引用、拒答等基础治理能力应该继续免费，
因为它们正是用户愿意采用和信任项目的理由。

## 许可证与产品包装

- 当前核心继续使用 MIT，不在项目还处于 Alpha 和接口演进期时改许可证。
- 托管控制面、代运维和客户专属连接器可以放在服务或单独分发的企业包中，并明确标注其
  与开源核心的边界。
- 社区版必须保留无需厂商账号即可完成的本地路径，第三方适配器保持可替换。
- 未来若单独的软件包使用其他许可证，应公开依赖关系，不能悄悄修改已经开源文件的许可。
- 在企业包出现之前，也可以通过付费试点、部署、培训和顾问服务获得收入。

MIT 允许别人分叉和商业使用，所以真正可积累的优势是维护者信誉、兼容性、真实部署经验、
持续维护的集成和案例证据，而不是让免费版残缺。

## 你可以自己完成的前端与社区工作

这些任务边界清楚，不依赖企业内部系统，适合维护者独立完成：

1. 把首次体验压缩成三步：生成演示数据、运行一次治理查询、查看决策 Trace。
2. 补齐空状态、加载/错误状态、键盘操作、可见焦点、移动端布局和中英文本。
3. 更新 v0.8 真实截图和 60～90 秒合成数据演示，所有截图都不出现客户资料和密钥。
4. 为 API、MCP、OpenAI 兼容网关和一个 Agent 框架各提供一个可复制的最小示例。
5. 建立连接器契约测试、合成 fixture、版本化 OpenAPI 文件和 TypeScript 客户端脚手架。
6. 维护 5～8 个范围很小的 `good first issue`，每个 Issue 都写清用户、完成标准和难度。

完成标准不是“页面更好看”，而是第一次使用者在 10 分钟内得到第一个治理答案，能看懂为何
采用或排除一条记忆，并知道下一步去哪里。

## 哪些工作值得找人合作

- **企业 AI 工程师 / Design Partner**：验证真实工作流，提供脱敏示例，测量旧答案率、
  审核耗时、引用完整率或敏感数据出境拦截数。
- **前端贡献者**：观察新用户使用控制台，改善信息层级、无障碍和桌面/移动端视觉回归。
- **连接器维护者**：负责自己实际使用的数据源，包括分页、检查点、删除、ACL 映射、限流和
  服务条款。
- **安全/合规工程师**：用具体威胁模型评审身份边界、密钥管理、保留删除和审计导出。
- **SDK/评测贡献者**：维护自己语言生态里的类型客户端、示例和可复现评测。

不建议你现在独自猜测并实现完整 SSO、多租户、高可用和所有企业连接器。这些功能不仅工作量
大，而且如果没有真实客户环境，很容易做成看起来完整、实际上无法落地的演示。

## 从反馈到首个付费试点

1. 找 3～5 位正在运行 RAG 或 Agent 的企业 AI 工程师，统一演示同一套合成数据控制台。
2. 每人进行一次 30 分钟访谈，只问一个具体问题：旧知识、无权限知识或弱引用目前造成了什么
   返工或风险？
3. 选择一个工作流和一个可测指标，例如制度回答新鲜度、审核队列耗时、引用完整率或敏感数据
   出境拦截数。
4. 先用合成数据跑通，再在书面批准的边界内使用脱敏数据；把身份、留存和导出决策写进试点记录。
5. 以“部署 + 一个连接器 + 评测 + 培训”组成 2～4 周付费试点。开源社区版不变，收费的是落地
   工作、责任和结果。
6. 只有当至少两个 Design Partner 提出同一类持续需求时，再把它产品化为托管能力或企业包。

## 未来 90 天的单人优先级

### 第 1～2 周：让人一眼看懂

- 更新 v0.8 截图、短演示和三步上手流程。
- 建立 Community / Enterprise 功能矩阵和“规划”标识。
- 发布 5 个真正能在半天到两天内完成的 Issue。

### 第 3～6 周：拿到真实反馈

- 邀请 5 位目标工程师，完成至少 3 次结构化访谈。
- 修复访谈中重复出现的上手或界面问题。
- 选定一个 Design Partner 和一项成功指标。

### 第 7～12 周：形成案例

- 完成一个合成优先、边界清楚的小试点。
- 输出一份经对方书面许可的匿名案例，写明基线、改变和局限。
- 决定下一项应该进入社区版、付费服务，还是暂不开发。

重点跟踪首次治理答案完成率、第二周仍在使用的人数、外部 PR、有效访谈和试点指标。GitHub Star
有助于传播，但不能代替真实使用和案例证据。
